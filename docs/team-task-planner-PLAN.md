# 팀 업무 마일스톤 관리 & 알림 TOOL 계획서

> 작성일: 2026-07-29 / 상태: **계획 단계 (구현 전)**

---

## 1. 배경과 목적

특정 팀원이 본인의 업무를 잊어버리고 방치하는 문제를 **개인의 기억력이 아니라 시스템**으로
해결하는 것이 이 TOOL의 목적이다. 핵심 철학은 다음 세 가지다.

1. **기록의 강제**: 모든 업무는 마일스톤과 일정(PLAN)이 기입된 상태로만 존재할 수 있다.
2. **자기 점검의 습관화**: 각 팀원은 본인이 세운 PLAN 대비 진행 여부를 스스로 체크한다.
3. **투명한 공유**: 일정 도달·지연 사실이 본인에게만이 아니라 **팀원 전원에게** 통지되어,
   "잊어버림"이 조용히 넘어갈 수 없는 구조를 만든다.

## 2. 요구사항 정리

| # | 요구사항 | 비고 |
|---|---------|------|
| R1 | 팀원별 업무를 마일스톤 방식으로 기록 | 업무 1건 = 마일스톤 목록 |
| R2 | 업무마다 PLAN 4단계 수립: `start → review1 → review2 → end` | 각 단계에 예상 일자 기입 |
| R3 | 팀원 본인이 PLAN 대비 진행 여부를 체크 | 상태 갱신은 본인 책임 |
| R4 | PLAN상 일정에 도달하면 해당 업무에 대해 **팀원 전원에게 개별 메일** 발송 | 업무 단위 알림 |
| R5 | **매일 아침 7시(KST)** 전 팀원의 진행 중 업무 요약을 전원에게 알림 | 데일리 다이제스트 |
| R6 | 팀원 수 변동(현재 3명) 대응 | 팀원 명단을 설정 파일로 분리 |
| R7 | PC에서 누구나 쉽게 공유·편집 가능한 형태 | 별도 앱 설치 없이 |
| R8 | 알림은 카카오톡 우선(PlayMCP), 어려우면 팀원별 지정 이메일 | 아래 5장 참고 |

## 3. TOOL 형태 — 데이터 저장/편집 방식

### 3.1 후보 비교

| 후보 | 공유·편집 용이성 | 자동화(알림) 연동 | 이력 관리 | 비용 |
|------|----------------|-----------------|----------|------|
| **A. Google Sheets** | ★★★ 브라우저만 있으면 동시 편집 | ★★★ API/Apps Script로 읽기 쉬움 | 수정 이력 자동 | 무료 |
| B. GitHub 저장소 내 YAML/Markdown | ★★ (git 사용법 필요) | ★★★ GitHub Actions와 궁합 최고 | commit 이력 | 무료 |
| C. Notion | ★★★ | ★★ API 가능하나 토큰 관리 필요 | 있음 | 무료~ |
| D. Excel 파일 공유(네트워크 드라이브) | ★★ 동시 편집 충돌 위험 | ★ 자동화 어려움 | 취약 | 무료 |

### 3.2 권장안: **A. Google Sheets (마스터 데이터) + GitHub Actions (자동화 엔진)**

- 팀원은 **스프레드시트 한 장**만 편집하면 된다 — 학습 비용 최소, PC/모바일 모두 가능 (R7 충족).
- 자동화 스크립트(Python)는 시트를 읽어 알림을 발송한다. 스케줄 실행은 GitHub Actions cron으로
  무료 운영이 가능하다.
- 팀원 명단·이메일 주소도 시트의 별도 탭으로 관리 → 인원 변동 시 행 추가/삭제만 하면 됨 (R6 충족).
- 대안: git에 익숙한 팀이라면 B안(저장소 내 YAML)이 더 단순하다. 시트 API 인증이 부담되면
  1차 버전은 B안으로 시작하고, 편집 편의 요구가 커지면 A안으로 이전하는 경로도 유효하다.

### 3.3 데이터 구조 (시트 설계)

**탭 1: `tasks` — 업무 원장**

| 컬럼 | 예시 | 설명 |
|------|------|------|
| task_id | T-2026-014 | 고유 ID (자동 채번 규칙) |
| owner | 김OO | 담당 팀원 |
| title | 7월 정산 보고서 | 업무명 |
| milestone | 데이터 수집 완료 | 현재 목표 마일스톤 (업무를 잘게 쪼갠 단위) |
| plan_start | 2026-08-01 | PLAN: 시작 예정일 |
| plan_review1 | 2026-08-05 | PLAN: 중간 리뷰1 예정일 |
| plan_review2 | 2026-08-08 | PLAN: 중간 리뷰2 예정일 |
| plan_end | 2026-08-12 | PLAN: 완료 예정일 |
| status | in_progress | `not_started / in_progress / done / hold` |
| stage_done | review1 | 실제로 통과 완료한 마지막 단계 |
| last_check | 2026-08-04 | 본인이 마지막으로 점검·갱신한 날짜 |
| note | 원천 데이터 지연 | 자유 메모 |

**탭 2: `members` — 팀원 명단** (인원 변동 대응)

| name | email | active |
|------|-------|--------|
| 김OO | kim@example.com | Y |

**탭 3: `log` — 발송 이력** (같은 알림 중복 발송 방지용, 스크립트가 자동 기입)

### 3.4 상태 판정 로직

- 오늘 날짜가 `plan_X` 일자에 **도달**했는데 `stage_done`이 그 단계 미만이면 → 해당 업무는
  "일정 도달/지연" 상태 → **R4 개별 메일 발송 대상**.
- `last_check`가 N일(기본 3일) 이상 갱신되지 않은 업무 → "방치 의심"으로 데일리 다이제스트에
  별도 표기 (본 TOOL의 존재 이유인 '까먹음 감지'의 핵심 장치).

## 4. 알림 설계

### 4.1 알림 종류

| 알림 | 트리거 | 수신자 | 내용 |
|------|--------|--------|------|
| **① 일정 도달 알림** (R4) | 어떤 업무의 plan 단계 일자 도달 | **팀원 전원, 개별 발송** | 업무명, 담당자, 도달한 단계, 통과 여부, 지연 일수 |
| **② 데일리 다이제스트** (R5) | 매일 07:00 KST | 팀원 전원 | 전원의 진행 중 업무 표 + 지연/방치 의심 업무 강조 |
| ③ (제안) 지연 에스컬레이션 | 지연 3일 이상 지속 | 팀원 전원 | 제목에 ⚠️ 표기, 지연 사유 기입 요청 |

### 4.2 카카오톡(PlayMCP) 실현 가능성 — **사전 조사 결과**

현재 PlayMCP가 제공하는 카카오톡 도구를 실제로 확인한 결과:

- 제공 기능은 **`카카오톡 나에게 보내기(메모 챗)` 단 하나**이며, **최대 200자** 제한이 있다.
- 즉 **"모든 팀원에게" 카카오톡을 보내는 것은 현재 PlayMCP로는 불가능**하다.
  (본인 계정의 '나와의 채팅'으로만 발송됨)

따라서 결론:

| 방안 | 판정 |
|------|------|
| PlayMCP로 팀 전원 카카오톡 발송 | ❌ 불가 (자기 자신에게만 가능) |
| 카카오 비즈니스 채널 + 알림톡 API | 가능하나 사업자 채널 개설·심사·건당 과금 필요 → 3인 팀에는 과함 |
| **이메일 발송 (팀원별 지정 주소)** | ✅ **채택.** SMTP(Gmail 앱 비밀번호 등)로 무료·안정적 구현 |
| PlayMCP 메모챗 병행 | △ 옵션. 각자 본인 세션에서 연동하면 "내 알림"을 카카오톡으로도 수신 가능 |

**결정: 기본 채널은 이메일(R8의 fallback안)로 하고, 카카오톡은 개인별 선택 옵션(메모 챗)으로
병행한다.** 이메일은 200자 제한이 없어 다이제스트 표 형식 전달에도 적합하다.

### 4.3 스케줄 구현

- GitHub Actions cron: `0 22 * * *` (UTC) = **매일 07:00 KST** → 다이제스트 + 일정 도달 검사 실행.
- 하루 1회 실행으로 R4·R5를 모두 처리한다. (일정 도달 검사는 "오늘 도달한 단계"를 아침에 통지)
- `log` 탭 대조로 동일 알림 중복 발송을 방지한다.

### 4.4 메일 서식 (초안)

```
[업무알림] ⚠️ 리뷰1 일정 도달 — 7월 정산 보고서 (담당: 김OO)

업무: 7월 정산 보고서 (T-2026-014)
단계: review1 (예정일 2026-08-05, 오늘 도달)
통과 여부: 미통과 (stage_done = start)
담당자 최근 점검일: 2026-08-01 (3일 전)
비고: 원천 데이터 지연
```

## 5. 유사 TOOL 벤치마킹

| 툴 | 우리와 유사한 점 | **벤치마킹할 점** |
|----|----------------|------------------|
| **Asana / Monday.com** | 업무별 마일스톤·타임라인, 마감 알림 | ① 마감 '도달 시'가 아니라 **N일 전 사전 리마인드** ② 지연 업무 자동 색상 표시 |
| **Jira** | 스프린트 리뷰 게이트 | ① review1/review2를 단순 날짜가 아닌 **통과 조건(체크리스트)이 있는 게이트**로 운영 ② 지연 시 사유 기록을 필수화 |
| **Trello** | 칸반 시각화 | 시트에 상태별 필터 뷰(진행 중/지연/완료)를 만들어 한눈에 보이게 |
| **Todoist / MS To Do** | 데일리 다이제스트 | "오늘 할 일 요약" 메일의 간결한 포맷 — 다이제스트는 표 1개 + 강조 3줄 이내로 |
| **Notion 스프린트 템플릿** | 주간 회고 | 주 1회(금요일) **주간 회고 다이제스트** 자동 발송: 이번 주 완료/미완료 집계 |
| **GitHub Projects** | 일정-실적 대비 | PLAN(예상) vs 실적(실제 통과일)을 같이 기록해 **개인별 일정 추정 정확도**를 축적 |

## 6. 기존 툴 대비 보완 제안 (설계에 반영할 것)

기존 툴들의 공통 약점은 "**알림을 무시하면 그만**"이라는 점이다. 이 TOOL의 목적(까먹음의
시스템적 관리)에 맞춰 다음을 추가로 설계에 반영할 것을 제안한다.

1. **방치 감지 (last_check 규칙)** — 마감이 남았어도 담당자가 N일간 상태를 갱신하지 않으면
   다이제스트에 "방치 의심"으로 노출. *마감일 알림만으로는 '잊고 있음'을 조기에 못 잡는다.*
2. **전원 수신 원칙의 유지** — 대부분의 툴은 담당자에게만 알림을 보내지만, 이 TOOL은 요구대로
   전원 발송을 유지한다. 동료의 시선이 곧 리마인더가 된다. 단, 알림 피로를 막기 위해
   ①번(일정 도달)만 개별 메일로, 나머지는 다이제스트에 통합.
3. **지연 사유 필수 기입** — 일정 도달 알림이 나간 업무는 note에 사유가 기입될 때까지
   다이제스트 최상단에 고정 노출.
4. **PLAN 변경 이력 보존** — 예정일을 슬쩍 미루는 것을 방지하기 위해, 예정일 수정 시
   원래 날짜를 log에 남기고 다이제스트에 "일정 변경됨(8/5→8/12)"으로 1회 표기.
5. **사전 리마인드** — 도달 당일뿐 아니라 **D-2 예고 알림**(다이제스트 내 표기)으로
   '도달 후 통보'가 아닌 '도달 전 준비'를 유도.
6. **입력 부담 최소화** — 팀원이 매일 해야 할 일은 "본인 행의 status/stage_done/last_check
   갱신" 뿐이도록 유지. 입력이 번거로우면 이런 툴은 반드시 죽는다.
7. **주간 리포트** — 금요일 오후, 주간 완료율·평균 지연일 요약 발송(선택).

## 7. 시스템 구성(안)

```
[Google Sheets]  ← 팀원 3명이 브라우저에서 직접 편집 (업무·PLAN·상태)
      │  (Sheets API, 서비스 계정 읽기 전용)
      ▼
[Python 스크립트]  daily_check.py
  - 오늘 도달한 PLAN 단계 검사 → 일정 도달 알림 생성
  - 전원 진행 현황 다이제스트 생성
  - 방치 의심(last_check 경과) 검사
  - log 탭 대조로 중복 발송 방지
      │
      ├─▶ [SMTP] 팀원별 이메일 개별 발송 (기본 채널)
      └─▶ [PlayMCP 메모챗] 본인 카카오톡 '나와의 채팅' (개인 선택 옵션, 200자 요약)

[GitHub Actions]  cron 0 22 * * * (UTC) = 매일 07:00 KST 실행
  - Secrets: 시트 서비스계정 키, SMTP 계정
```

## 8. 구현 로드맵 (예상 일정)

| 단계 | 내용 | 산출물 | 예상 소요 |
|------|------|--------|----------|
| **M1** | 시트 템플릿 제작 (tasks/members/log 탭, 데이터 검증·조건부 서식) | 공유 시트 | 0.5일 |
| **M2** | `daily_check.py`: 시트 읽기 + 상태 판정 + 메일 발송 | 스크립트 | 1일 |
| **M3** | GitHub Actions cron 배치 + Secrets 설정 + 시험 발송 | 워크플로 | 0.5일 |
| **M4** | 1주 시범 운영 → 알림 문구·빈도 조정 | 운영 규칙 v1 | 1주 |
| **M5** | (선택) 방치 감지·일정 변경 이력·주간 리포트 등 6장 제안 반영 | v1.1 | 1일 |

## 9. 리스크와 대응

| 리스크 | 대응 |
|--------|------|
| 팀원이 상태 갱신 자체를 안 함 | 방치 감지(6-1)로 다이제스트에 자동 노출 — 갱신 안 함도 '보이게' 만든다 |
| 알림 피로로 무시 습관화 | 개별 메일은 일정 도달 시에만, 나머지는 하루 1통 다이제스트로 통합 |
| Gmail SMTP 일일 발송 한도 | 3인 팀 규모(하루 수 통)에서는 문제 없음. 초과 시 SendGrid 등 검토 |
| 시트 실수 편집(컬럼 삭제 등) | 데이터 검증 + 시트 버전 기록 복원, 스크립트에서 스키마 검사 후 이상 시 관리자에게만 오류 메일 |
| GitHub Actions cron 지연 | 수 분 지연 가능(무료 러너 특성). 07:00 정각이 중요하면 cron을 21:50 UTC로 앞당김 |

## 10. 확정 필요 사항 (팀 결정)

1. 저장 방식 최종 확정: **Google Sheets(권장)** vs 저장소 내 YAML
2. 팀원 3명의 알림용 이메일 주소
3. 방치 판정 기준일(기본 3일), 사전 리마인드 D-2 적용 여부
4. 주간 리포트(금요일) 도입 여부
